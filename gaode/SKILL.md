# 周边去哪儿：基于高德的地点推荐助手（SKILL.md）

## 一、Skill 名称、用途与适用场景

- **Skill 名称**：`gaode-nearby-recommendation`（周边去哪儿：基于高德的地点推荐助手）
- **核心用途**：根据用户给定的城市、起点（坐标或地点）和自然语言需求，调用高德 MCP Server 的**地点搜索**与**步行路线规划**工具，查询起点附近的候选地点，逐一核实从同一起点出发到各候选地点的实际步行距离与步行耗时，严格按步行时间上限、推荐数量上限及排序偏好筛选后，生成真实、简洁、可核验的地点推荐。
- **适用场景**：
  - 用户询问“附近有什么值得去的咖啡馆/餐厅/书店/公园/便利店等”；
  - 用户带有明确的步行时间限制（如“步行不超过 15 分钟”）、推荐数量上限（如“推荐最多 3 家”）或排序偏好（如“优先近一点的”）；
  - 用户需要了解每个推荐地点的真实名称、详细地址、从起点出发的预计步行距离与步行时间，以及客观推荐理由。

---

## 二、执行步骤与工具调用规范

在接收到用户的单轮需求后，Agent **必须严格按照以下 4 个步骤执行**，不得跳过工具调用或凭空编造任何地点与路线数据：

### 步骤 1：需求解析（理解约束条件）
从用户输入中提取以下关键参数：
1. **城市与起点坐标（Origin）**：读取输入中提供的明确起点坐标（格式通常为 `经度,纬度`，如 `120.123456,30.123456`）及起点名称、所在城市。若仅提供起点名称而未给坐标，先使用高德地理编码或地点搜索工具获取起点坐标。
2. **目标地点类型/关键词（Keywords）**：如“咖啡馆”、“餐厅”、“公园”、“自习室”等。
3. **步行时间上限（Max Walking Time）**：如“步行不超过 15 分钟”（即 `900 秒`）。若用户指定了分钟数 T，则硬性上限为 `T * 60` 秒。
4. **推荐数量上限（Limit）**：如“推荐最多 3 家”（默认最多返回 3 个符合条件的地点，严禁超过用户指定的上限数量）。
5. **排序偏好（Sort Preference）**：如“优先近一点的”（按实际步行耗时/步行距离从短到长升序排列）。
6. **软性/主观条件（Unverifiable Attributes）**：如“安静一点”、“不排队”、“有插座”、“正在营业”等高德基础 POI 或路线接口可能未直接返回的信息，记录为待核实项。

### 步骤 2：调用高德地点搜索工具（获取候选地点）
1. 使用高德 MCP Server 的**地点搜索能力**（优先使用周边搜索工具如 `maps_around_search`，传入起点坐标 `location`、关键词 `keywords` 及合适的搜索半径 `radius`，如 1500~2000 米；或使用文本搜索 `maps_text_search` 配合城市与起点周边关键词）。
2. 从返回结果中提取候选地点列表，记录每个候选地点的：
   - **地点名称（`name`）**
   - **详细地址（`address`）**
   - **目标坐标（`location`，经度,纬度）**
   - **类型/评分/特色等工具返回的真实附加字段（如有）**
3. **初步过滤**：剔除类型明显不符（例如用户找咖啡馆但返回了停车场/公交站）或缺少有效坐标的条目。选取前 5~8 个相关度高、距离较近的候选地点进入下一步步行路线核验。

### 步骤 3：调用高德步行路线规划工具（核验真实步行距离与耗时）
1. 对筛出的每个候选地点，**必须逐一调用高德 MCP Server 的步行路线规划工具**（如 `maps_direction_walking`）：
   - 起点（`origin`）：固定为用户给定的**同一起点坐标**（所有候选地点都是从同一起点出发的独立备选，**严禁将多个地点串成多站连续行程**）。
   - 终点（`destination`）：该候选地点的坐标。
2. 从步行路线规划返回结果中读取真实的：
   - **步行距离（`distance`，单位：米）**
   - **预计步行耗时（`duration`，单位：秒，换算为分钟：向上取整或四舍五入为分钟数，并同时标注精确秒数或分钟数）**
3. **严禁使用直线距离估算步行时间**，回答中的所有距离与时间数据必须 100% 来自高德步行路线规划工具的返回结果。

### 步骤 4：严格筛选与偏好排序
1. **硬性时间上限过滤**：
   - 将每个候选地点的实际步行耗时与用户的步行时间上限比较（例如“步行不超过 15 分钟”即 `duration <= 900` 秒，或换算分钟数 `<= 15` 分钟）。
   - **凡是超过步行时间上限的地点，必须从合格推荐列表中剔除，严禁将超时地点列为符合条件的推荐！**
2. **排序规则**：
   - 当用户要求“优先近一点”或类似距离/时间偏好时，严格按照**步行路线规划返回的实际步行时间（及步行距离）从小到大升序排列**，确保第 1 个推荐是步行最快/最近的地点，且文字解释与路线数据完全一致。
   - 若用户无距离排序偏好，也建议默认按步行耗时由近及远排序，方便用户就近选择。
3. **数量截断**：
   - 仅保留排序后的前 N 个符合全部硬性条件的地点（如最多 3 家）。
   - 若符合条件的地点不足 N 家（例如只有 1~2 家甚至 0 家），**有多少家就只推荐多少家，绝不拿超时或不符合类型的地点凑数**。

## 三、回答格式与异常处理规范

### 1. 标准推荐回答格式
请使用清晰的 **Markdown 表格 + 分点列表** 呈现最终符合条件的推荐结果（每个地点必须包含以下 4 项核心要素：地点名称、详细地址、预计步行距离与时间、推荐理由）：

#### 推荐结果概览（表格）
| 序号 | 地点名称 | 详细地址 | 预计步行距离与时间（从起点出发） | 推荐理由 |
| :--- | :--- | :--- | :--- | :--- |
| 1 | **[与高德返回完全一致的名称]** | [与高德返回完全一致的地址] | 步行 **X 米**，预计 **Y 分钟**（约 Z 秒） | [基于真实路线/类型数据的简短理由，如：距离起点最近，步行仅需 Y 分钟，符合咖啡馆需求] |

#### 详细推荐说明（列表）
1. **[地点名称]**
   - **地址**：[高德返回的真实地址]
   - **步行路线**：从起点独立出发步行 **X 米**，预计耗时 **Y 分钟**（约 Z 秒，数据源自高德步行路线规划）。
   - **推荐理由**：[一句简洁、有数据依据的推荐理由，如“在符合条件的候选地点中步行距离最近、耗时最短，满足 15 分钟内可达要求”]。
   - **信息核实说明**：[若用户提到安静程度、排队情况、营业状态、是否有插座/Wi-Fi 等高德未返回的信息，此处必须明确标注“**未核实**（高德接口未返回实时安静程度/排队情况/营业状态数据，请以现场实际情况为准）”，严禁编造]。

### 2. 边界与异常情况处理规则

1. **符合条件的地点不足指定数量（如少于 3 家）**：
   - 如实列出所有符合条件（未超时、类型匹配）的地点（1 家或 2 家）。
   - 在回答末尾补充说明原因，例如：“*说明：在起点周边查询到的候选地点中，仅有以上 X 家满足步行不超过 Y 分钟的要求，其余候选地点步行耗时均超过 Y 分钟，因此未纳入合格推荐。如需更多选择，建议适当放宽步行时间上限。*”
2. **完全没有找到符合条件的结果（0 家合格）**：
   - **明确告知未找到符合条件的推荐，严禁编造地点或强行将超时地点作为合格推荐返回**。
   - 如实说明原因（例如：“在起点周边检索到的咖啡馆步行耗时均超过 15 分钟，暂无满足步行时间上限的推荐”），并建议用户放宽步行时间上限（如放宽至 20~25 分钟）或扩大搜索范围。
3. **缺少依据的主观/实时信息（信息缺失处理）**：
   - 对**安静程度、环境氛围、当前排队情况、实时营业状态、人均消费、插座/Wi-Fi 情况**等高德工具返回结果中未包含的字段，**一律明确标注“未核实”**，绝不使用“环境非常安静”、“目前不用排队”、“正在营业中”等未经工具数据证实的表述。
4. **工具调用失败或服务异常**：
   - 若高德地点搜索或步行路线规划工具返回错误、超时或空响应，可尝试重试一次；若仍失败，**必须如实向用户说明高德查询服务暂时异常或未能获取到有效数据**，建议稍后重试或调整查询条件，绝不自行凭记忆生成任何地点名称、地址或步行时间。
